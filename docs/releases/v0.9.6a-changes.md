# Changes since v0.9.5a

Reference material for writing the v0.9.6a release notes. Not release notes.

Every entry below is copied **verbatim** from the `Pending` section of
`docs/sysop/CHANGELOG.md`, which is the authoritative record. Nothing has been
reworded. What has been added is classification and grouping.

Headings are the changelog's own section names, kept so an entry can be traced
back. "Features" and "Bugfixes" are two large sections in the changelog that were
already classified when written; the rest were sorted here.

366 commits, 359 changelog entries.

**Confidence note.** Entries explicitly starting with "Fix:" are certain. The
release, update and install sections are certain to be new, since none of that
subsystem existed at 0.9.5a. The remaining 63 were classified by reading them,
and a handful are genuinely both: replacing a broken thing with a better one.
Anything marked OTHER is a refactor, a scope statement or dependency maintenance
rather than a user-visible change.

## New features

### Configuration

- A `.env` edit can now be applied without restarting. A Reload button beside Exit on `/admin/config` (POST `/admin/config/reload`) re-reads both the file and the database, then publishes `CONFIG_CHANGED` to the other three processes. Keys marked `restart: true` still need a real restart.
- Settings with a fixed set of legal values now render as a select with a hint for the value in effect, and the save route refuses anything outside the list rather than storing it, naming the key it left alone. Every consumer of a setting like this reads it as text and falls back to something safe on an unrecognised value, so a typo did not fail loudly: relay would quietly resolve to `off` while the settings page displayed "nodelists" as though it were in effect. Currently `netmail_relay_mode` and `zmodem_default_crc`.
- New sysop guide `docs/sysop/NETMAIL_RELAY.md`, since the relay modes had no sysop-facing documentation at all. It covers which mode to pick, why `on` is broader than it reads given that route resolution walks the nodelist and the coordinator tree, what nodelist mode actually checks, the fact that no nodelist imported for a network means no relay for that network, what it does not protect against, and the `allow_netmail_relay` upgrade.
- **The settings table now records whether a value was chosen or merely seeded.** `configStore` seeds every default into `settings` on first run, so a row existed for every key whether or not anyone had touched it, and a deliberate choice was indistinguishable from an untouched key. That is why `allow_netmail_relay` had to be deprecated and ignored rather than migrated: honouring a stored `false` would have pinned every upgrade to the old behaviour, and honouring `true` would have switched relay on for someone who had turned it off. A new `source` column records `default` or `sysop`, and `configStore.wasSetBySysop(key)` answers the question. This does not reopen the relay decision, which was settled on separate grounds (relay was broken before, so there was no working configuration to preserve); it is there for the next deprecation.
- Existing installs are backfilled by migration `0004-settings-provenance` using two signals that are exact rather than guessed: a row written after it was inserted (`updated_at > created_at`, which the seed cannot produce), and a key that is not in `configDefaults` at all and therefore was never seeded. On the development box that identified 36 settings as chosen and 122 as shipped defaults. One case is genuinely unrecoverable and is not guessed at: a sysop who deliberately set a key to exactly its default value leaves no evidence that they did.

### Message Bases: Import, Retention and Moderation

- **JAM message base import** alongside the existing Synchronet SMB support, for migrating a Mystic hub. Struct offsets follow the JAM(mbp) spec as published in JAM.H; `MSG_DELETED` is `0x80000000`, the sign bit, so attribute tests go through a helper rather than bare truthiness. Bulk import scans a directory, matches each base to an area by areatag then shortcode, and runs on the worker queue with a mapping form that carries decisions rather than filesystem paths.
- **Optional retention limits on message areas.** `max_age_days` and `max_messages` on `message_areas`, with the same pair on `message_groups` as defaults seeded into new areas. **Both NULL by default, and NULL means keep everything**, so every existing area and every fresh install prune nothing until a sysop opts in. Enforced by a new `message-maintenance` job at 04:00 daily. Age measures the message's own date rather than when it arrived, which is what a sysop means by "keep 90 days" and matches Synchronet and Mystic. That carries a sharp edge: a JAM or SMB import keeps its original dates, and real imports show up to 1,999 days between message date and import date, so setting a limit on a freshly imported base prunes nearly all of it on the next run. `GET /admin/msgArea/:shortcode/retention/preview` accepts proposed limits as query parameters, reports what would go, and deletes nothing. Preview and the real run share `pruneArea()` so they cannot disagree.
- Pruning is per message, not per thread. In FTN a reply whose parent has rolled off is the normal state of the network. Survivors get `message_count` and `last_message` recomputed, emptied threads are dropped along with their `user_thread_pointers`, and area counters are refreshed, because the reader lists threads straight from the thread table and orders by `last_message`.
- Retention now outranks peer high water marks. Pruning previously stopped at the lowest enabled `msg_idx` so nothing was deleted before every peer had collected it. Right instinct, wrong rule: one downlink that stopped polling a year ago pins the floor at its old position and retention silently does nothing, for ever. Export runs `WHERE id > msg_idx`, so a pruned row is simply absent and the peer receives what survives; any subscription left below the pruned range is advanced to the highest pruned id. Both the run and the preview report `peersAdvanced` and a `peersBehind` list carrying `previousIdx` and `messagesLost` per peer, and each advance is logged naming the peer, so the cost is visible before and after.
- Group defaults can now push retention to existing areas, via a Retention tickbox in the Push Group Defaults modal. It is unticked by default, unlike the others: both retention columns are nullable and null means no pruning, so pushing retention from a group with no limits set turns pruning **off** on every area in the group. The modal says so explicitly when the group is in that state.
- **Moderation is now a property of the message.** Every view that shows a message was being handed a page-level `canModerate` flag and left to work out what it meant, so the rule lived in the routes and in the browser and the terminal reader never got any of it. `messages.js` answers once and the answer travels with the item: `moderationForArea` gives the area answer including every destination, `moderationFor` narrows it per message or thread, and `attachModeration` stamps `.moderation` across a list in one pass including a refusal, so a view never has to tell "not computed" apart from "no". No consumer reads permission flags or `source_network_id` any more.
- Delete controls sit where the content is visible: a delete in the thread header for the whole thread and one on every message in the thread view, and one per message in the flat view. Not on the area thread list, which shows subject lines only, so deleting from it would be blind. The confirm dialog says plainly that deleting the first message takes the whole thread with it, and that a deletion is local: anything already sent to peers stays where it is and a rescan can bring the thread back. Gated on `areaAccess.canModerateArea(user, area)`, which is the Sysop flag today and is its own function because per-group and per-area moderators are wanted next. The check is in the routes as well as the templates: hiding a button is presentation, not access control.
- The terminal reader gets delete and move on D and M, confirmed, with a scope question when a thread is on screen and a lightbar list of the destinations that message's own answer allows. The dumb-terminal path gets the same operations with a numbered list.

### Message Networking: Netmail Relay

- **Netmail relay is now `netmail_relay_mode`: `off`, `nodelist` or `on`, defaulting to `nodelist`.** The old boolean's "on" was far more open than it read. `resolveRoute` finds a way to anything dialable in the nodelist and walks up to a hub, host, RC or ZC for anything else, so `allow_netmail_relay=true` meant transit for the whole of every network this system carries, in any direction, including between two of them. A node on one othernet could reach any node on another through this system, which is an open relay however well trusted each individual link is. Nodelists here are scoped per network, so requiring both ends to be listed in the same one is the whole fix: cross-network relay is refused because the ends resolve to different networks, invented addresses are refused because they are listed nowhere, and a zone we hold no address in is refused because we do not carry that network. Ordinary routed netmail is untouched. The rule is network-scoped rather than net-scoped on purpose, since a coordinator routes outbound mail for their nodes and FidoNet spans zones 1 to 6. Points are stripped before the lookup, as points are never listed. An unrecognised mode value fails closed to `off` rather than to the default. Refusals now say which rule refused them and name the address they could not find, instead of always reporting "relay is disabled".
- **Netmail addressed to Ping now gets a Pong back** showing the route it took. A convention rather than a numbered standard, but Husky, Mystic and Synchronet all answer it, so other sysops expect it to work; until now a ping aimed here fell through to the undeliverable queue and generated a sysop notification. The reply comes from the address the ping was aimed at rather than the default AKA, so a node pinging one of several addresses can tell which answered, and it carries no Via lines of its own or our own loop check would refuse it. New key `netmail_ping_enabled`, default true.
- **Netmail relay decision log.** Relay left traces before this, but no two of them in the same place: a success wrote an alog line and a `pm_outbox` row, a refusal wrote a different alog line, a loop wrote an undeliverable row, and an unroutable address wrote a text dump into `ftn/bad`. Two of those four roll over, so "did we relay what we should have, and did it leave" was not answerable after the fact. `netmail_relay_log` now takes one row per decision, written at the decision point, whatever the decision was. Refusals are recorded on purpose: a gate nobody can see refusing anything is a gate nobody can validate. Each row keeps who wrote the message apart from who handed us the packet, which are the same on originated mail and different on transit, and are the only way to see which link is actually feeding you transit traffic. Also recorded: the Via chain as it arrived, the AKA we stamped, the next hop and how the route resolved, the mode in effect, and the `pm_outbox` uuid the message became. That uuid makes the useful query possible: `pendingDelivery()` finds relays that were queued and never sent, which nothing else could show, because queueing looked like success at every point the old logging covered and a message then sitting unsent produces no further event of any kind. Retention `netmail_relay_log_retention_days`, default 180, longer than the other logs because relay disputes surface weeks later.
- Admin page at `/admin/relay-log`, under Networking alongside the file logs it resembles. It leads with the thing worth acting on, which is messages accepted for relay and queued more than N hours ago whose outbound row still has not gone. Below that, counts by decision over a selectable window, every decision with a per-row detail view showing the Via chain as it arrived and how the route resolved, filter buttons per decision, and transit mail grouped by who handed us the packet, which is where a misconfigured or probing link shows up. CLI equivalent at `node src/tools/relayLog.js`.

### Message Networking: AreaFix, FileFix and Echolists

- **`%RESCAN` on both AreaFix and FileFix.** Neither fixer had a rescan, so a downlink that subscribed to an area got nothing until the next new message arrived and had no way to ask for backfill. Grammar, identical on both: `%RESCAN` (every subscribed area, default window), `%RESCAN ALL` or `*`, `%RESCAN AREATAG`, `%RESCAN AREATAG 30` for a day count, and `%RESCAN ALL /FULL` for everything still held. Bare `%RESCAN` meaning "all" is what SBBSecho, Mystic and Squish implement, so it must not return an unknown-command reply. `/FULL` is the documented flag because a leading dash already means unsubscribe in the AreaFix grammar. Defaulting to a window rather than everything is deliberate, since a full rescan of a busy area pushes thousands of messages down a link: `areafix_rescan_default_days` (60), `areafix_rescan_max_days` (0, no ceiling, does not restrict `/FULL`) and `areafix_rescan_enabled` make that a sysop decision. Two limits are stated in the response text rather than left to surprise the downlink: retention caps what can be replayed, and imported history is never replayed.
- Only the parser is shared between the two sides, because the mechanisms genuinely differ: `peer_area_subscriptions` has a `msg_idx` high water mark so a message rescan rewinds a pointer, while file subscriptions have no pointer at all and distribution is per file per peer, so a file rescan re-queues `file_distribution` rows to pending and creates them where a file was never queued for that peer. The pointer anchors on the oldest in-window id minus one rather than the newest row older than the cutoff, because `msg_idx` is an id and the window is a date and the two do not move together: an imported message carries a high id and a very old date, so the obvious anchor lands above in-window messages with lower ids and silently skips exactly what was asked for. A rescan only ever moves a pointer backwards.
- **Rescan button on every peer connection row** in the admin peer page, opening a modal taking an areatag (blank or ALL for everything), a window in days, and a Full checkbox. It mirrors the netmail grammar and calls the same model functions, so the UI and `%RESCAN` cannot drift apart. FTN connections previously had no reset control at all: the existing Reset Idx buttons appear only for NNTP and QWK, so the main case had no way to resend held mail from the UI.
- **Batch subscribe for echolists.** Subscribing from an echolist was one modal per area, and BACKBONE.NA carries 241 areatags. New page at `/admin/echolist/:networkId/batch` (with `?echolistId=N` to scope to one list) lists only uncarried areatags with a checkbox each, a filter box, and a select-all that respects the active filter so a prefix can be taken without touching the rest. One shared settings block covers the whole batch: target group, read and post security, post_as, newscan default, the four flag lists, and the peer allow/enable toggles. The work runs as `echolist:batch-subscribe` on the maintenance queue rather than in the request, because each area costs a uniqueness check, a QWK conference allocation, an INSERT, two backing tables, a scan pointer per active user, the network mapping and a peer sync. A sysop notification reports created, failed, skipped and renamed counts when the run lands. Create-only: mapping an existing local area onto an areatag is a per-area pairing decision that does not generalise to a batch.
- `planBatch()` is a read-only pre-flight exported separately, so a dry run cannot disagree with what the job does. It resolves shortcode collisions against both the database and codes claimed earlier in the same run, since sanitising is lossy and FSX.GEN and FSX-GEN both want FSX_GEN, and it dedupes repeated areatags, because an areatag is unique per network so a repeat means a doubled checkbox rather than a second area. Failures are isolated per area so one bad tag does not abandon the rest.
- **Batch subscribe for filebones**, at `/admin/filebone/:networkId/batch`, job `filebone:batch-subscribe`. Kept as a parallel module rather than folded into a shared abstraction, matching the convention that `fileEcholist.js` mirrors `networkEcholist.js`: file areas have no backing tables, creating and mapping are separate calls, peer sync takes both flags in one pass, there is no QWK conference number, and it adds browse security, browse flags and the `max_age_days` / `max_files` retention limits. `sub_dir` is deliberately not a batch setting, since `newArea()` defaults it to the lowercased shortcode and one shared value would put every area in one directory.

### Mailer

- **Mailer session history.** The mailer knew all of this while a session was running and kept none of it. The only durable trace was the backoff state on `connection_data`, which is overwritten on every attempt, so it answers "is this peer in trouble now" and cannot answer "what happened the last five times we called". `mailer_sessions` records one row per attempt in both directions, with outcome and reason, files and bytes each way, duration, the peer's M_NUL VER/SYS/ZYZ banner, every AKA it presented, and the host. Attempts that never opened a socket are recorded too, which matters more than the rest: the peer failing hardest is the one that never gets far enough to have a session, and recording only completed handshakes would leave it looking like the quietest node on the board. Writes are diagnostic, so a failed insert is swallowed rather than taking a session down with it. Retention `mailer_session_retention_days`, default 30. Admin views at `/admin/mailer`.
- `outbound_file_log` mirrors `inbound_file_log`, written on M_GOT so a row means the peer acknowledged the file. Kept as its own table rather than a direction column, because the FTN tosser looks packets up in `inbound_file_log` by filename to trace senders. Retention `outbound_log_retention_days`, default 90.

### Worker Health and Queue Diagnostics

- The worker publishes a heartbeat carrying pid, uptime, per-queue consumer status, when it last finished a job, and the age of the longest job in flight. A clean shutdown writes a `stopped` marker, without which the watchdog cannot tell a sysop running `pm2 stop worker` from a worker falling over. The worker also self-checks: a closed consumer that has not recovered across several beats exits non-zero so the supervisor brings back a clean process.
- The watchdog runs in the gateway, because a dead gateway is obvious in minutes and a dead worker is silent for days (it is skipped in embedded mode). It escalates: log, notify the sysop once per incident, then restart. The restart is gated by grace window, cooldown and attempt cap, because a worker that cannot stay up is not fixed by restarting it a hundred times and a restart loop is worse than the outage. A bare `pm2` in `worker_restart_command` is resolved next to the running Node binary before falling back to PATH, since under nvm the daemon's PATH may never have reached the gateway. New keys: `worker_health_enabled`, `worker_heartbeat_interval`, `worker_health_check_interval`, `worker_health_grace`, `worker_selfcheck_max_failures`, `worker_restart_enabled`, `worker_restart_command`, `worker_restart_cooldown`, `worker_restart_max_attempts`, `worker_schedule_lag_grace`.
- **New queue diagnostic: `node src/tools/schedules.js`.** It reports the worker's own heartbeat, per-queue depth with the age of every active job, and every registered scheduler with its interval, next run and iteration count, then compares that against what the database says it should be and flags mismatches and orphans. `--sync` makes them match without a gateway restart, `--prune` removes orphans only. Next run is the headline and matters more than it reads: a BullMQ scheduler is not a timer, the next iteration is created when a worker picks up the current delayed job, so a stopped or wedged worker freezes every schedule where it stands while the registered intervals still look perfect. `--sync` deliberately skips overdue entries, because overdue is a consumer problem and re-registering would look like a fix and change nothing. The watchdog warns on an overdue schedule alongside a healthy worker, which usually means the processes disagree about `REDIS_BULLMQ_DB`.

### Admin Panel

- Tabbed layout for the message group and file group create/edit forms, and for all three file area forms, bringing them in line with the message area modals. The three file area forms were near-identical copies differing only by the group selector and the immutable short code, and now share a `fileAreaFormFields(prefix, mode, opts)` mixin.

### Web and Terminal

- The message areas list gets a sort toggle beside the search box: the sysop's ordering, or most recently active first. Sorting happens within each group rather than across the page, so the grouping still means something. It is client-side because the rows are already in the browser, and a round trip would drop the current search text and the Subscribed/All toggle. Areas that have never carried a message sort last rather than jumbling in among dated ones. The choice is remembered in `localStorage` under a namespaced key, with reads and writes wrapped, since `localStorage` throws outright in a private window and a sort control is not worth breaking a page over.
- The last-message column shows the year once a date stops being recent: "Mar 15" while recent, "Mar 2021" once not, which is what `ls -l` has done with the same problem for decades. Previously an area whose last message arrived in 2021 read exactly as freshly as one from last week. The threshold is six months rather than a calendar-year test, and that distinction is the point: "is this a previous year" would drop the day from a six-week-old December message the moment the year rolled over. The exact value is in a tooltip, so the abbreviated form never hides anything.

### Release Engineering

- **Cutting a release is now one command.** `node scripts/release.mjs --stable 0.9.6a` refuses a dirty tree, a failing suite, an empty changelog `Pending` section or a version that is not newer than what the tree already claims; closes `Pending` into the version and opens a fresh one; writes a release note skeleton; bumps `package.json`; commits and tags; and then builds the artifact. v0.9.5a shipped with no release notes at all and they had to be written retrospectively five months later from the changelog, which is the specific gap this closes: after a cut there is always a file carrying the upgrade actions and the change list, waiting for the prose.
- The bookkeeping deliberately happens before the artifact is staged, so a release tarball contains its own release notes and its own changelog entry. Building first would ship a tarball whose changelog says the release is still pending.
- **Upgrade steps and notices are now declared rather than only written as prose.** This release's Upgrade Notes carry nine actions and the update script runs two; the rest are the sysop's job to read, match against their install and perform, and several are silent when missed. `docs/releases/pending.json` accumulates the same actions in a form a machine reads: a step has something to run and a condition saying whether this install needs it, a notice has nothing to run and is a behaviour that changed underneath the sysop. Nothing consumes them yet, which is the update check and the updater, but a release published from here on carries them.
- The two halves are cross checked at cut time and never derived from one another. Parsing a changelog to decide what to execute on somebody's live board works right up until a bullet is reworded, and the failure is silent. What the script reports instead is a whole half missing: upgrade notes with nothing declared, or declarations with no upgrade notes.
- **A release now publishes a content-hash manifest of every shipped file.** `update.sh` compares mtimes to decide whether a sysop edited a file, which says when it was written and nothing about whether the contents differ from what shipped. The manifest also makes deletions expressible: it describes the complete target tree, so a file present locally and absent from the manifest is one to remove. A delta expressed only as changed files cannot say "this file is gone", which is exactly why `update.sh` reaches for `rm -rf` on code directories.
- **Development builds ship as deltas against the last stable.** `--dev` derives its version from `package.json` plus today's date, packs only the files that differ from the base, and carries the full manifest so the rest is reconstructible. A build touching five files ships five files rather than the whole tree, which matters down a file echo. Always against stable and never against the previous development build, so the base cannot be ambiguous and one pruned artifact cannot break a chain.
- The build stamps the computed version into the `package.json` inside the artifact. Without it every development build would install claiming to be the stable it was based on, be told by an update check that it is current, and never see a newer build at all. A consequence worth knowing: that one file always differs from the base, so "nothing has changed since the last build" needs the staged file re-hashed with the base's version put back, which is how the script refuses to publish a build with nothing in it.
- **What ships, and how each file may be treated on an install, now has one definition.** `src/release/shippedTree.js` replaces the directory lists that were written twice in `install.sh` and `update.sh` and drifted, which is what let `install.sh` delete every sysop-added asset under `public/`. The categories are behavioural claims (overwrite and delete strays, overlay, seed once, merge, skip art) and travel per file inside the manifest rather than being re-derived, so a release that adds a directory carries the rule for it. A path with no rule does not ship at all rather than defaulting: defaulting a new top-level directory to code would mean the first release after somebody adds one deletes whatever a sysop keeps in it.
- **A stable cut refuses to publish if it drops a migration its own development builds already applied.** Because a development build names its base in its own version, the set of builds that put migrations into people's databases this cycle is enumerable straight out of the release index. If a migration went out on development and got deferred out of the stable cut, everyone running one of those builds is about to be refused the upgrade by the runtime move rule; the script names the builds and the migrations and stops. The design called for a warning here; a warning in script output is one nobody reads, and `--allow-migration-gap` covers the case where retiring the migration is deliberate.
- Also published per release: a per-channel index listing every release newest first with its migration ids, so a client answers "is there anything newer, and can I move to it" in one fetch, and `SHA256SUMS` over everything, optionally GPG signed. Publishing itself is by hand for now. `docs/reference/RELEASE_PROCESS.md` is the maintainer guide.

### Update Checking

- **Canectic can now tell you when there is a newer release.** `/admin/update` reports what is available on each channel and whether this system can take it, and an opt-in daily job raises a sysop notification when something newer appears. It is **off by default**, because an outbound request from a sysop's box should be something they turned on rather than something they have to discover and turn off. It never downloads an artifact and never applies anything: installing an update is still `setup/update.sh`, and the in-BBS updater is the next phase.
- **No telemetry.** The check is a plain GET for a static JSON file, with no query string, no identifier, no version and nothing about the board or its users. A server logging it learns that an IP address asked for a file, which is what any web server learns about any fetch. With the check off and nobody pressing the button, this system makes no outbound request at all.
- A release is reported as **blocked**, with reasons, rather than hidden. Three things block a move: this database has applied a one-time migration the target release does not ship, the install is below the target's declared upgrade floor, or Node is older than the release needs. The first is the one that matters, and it is the case a version comparison cannot see: work that went out on a development build and then got deferred out of a stable cut makes the move forward by number and impossible in practice. "You cannot move to stable" is not actionable, so the page and the notification both name the migration.
- The migration rule reads only migrations the ledger recorded as `applied`. `skipped` means the migration decided this system did not need it and `preinstalled` means the database was born current, so in neither case is there a transformation for a target to understand. Reading every settled id instead would have refused every upgrade on a brand new board, since a fresh database records the lot as preinstalled.
- A system on the development channel is also told when stable is available, because converging back onto stable is a move worth being offered and would otherwise never be seen. A system on stable is never told about development builds: that is a channel they did not choose, and offering it would be the software talking somebody into running prerelease code.
- Notifications deduplicate on version **and** verdict. A daily job that says the same thing every morning is a job a sysop turns off, after which they hear about nothing at all. Both halves are in the key because a release that was blocked and is now reachable, because they ran the migration or upgraded Node, is news even though the version has not moved, and that is the notification they have been waiting for.
- A channel with no index published reads as "not resolved" rather than as an error. A project that has cut no development builds has no development index, and a 404 there is the normal state of affairs; putting a red error on every stable-only install's page daily would train sysops to ignore the page. A timeout, a server error, or a document that is not an index is a real error and is recorded as one. One channel failing does not discard the other.
- Every check is recorded, whether it found anything or not, and shown as history on the page. A page that shows only the last result cannot tell a check that found nothing from a check that stopped running, and the second is the failure worth seeing: an opt-in daily job that silently stopped looks exactly like a project that stopped releasing. Retention is `update_check_retention_days`, default 90.
- The daily schedule is registered only when the check is enabled, rather than registered and skipped. `src/tools/schedules.js` compares every registered scheduler against what the database says should exist, and a permanently inert entry would be a line that means nothing on the one page whose value is that everything on it means something. Turning the check on therefore needs a gateway restart or `schedules.js --sync`, like every other schedule-affecting setting.
- **Check now** on `/admin/update` runs regardless of the setting. The opt-out is about this system reaching out unprompted; a person pressing a button is not that, and refusing them would mean the only way to ask a question is to change a setting and restart.
- Only the settings that do something are configurable: `update_check_enabled`, `update_channel`, `update_check_url` and `update_check_retention_days`. The FTN transport keys in the design are deliberately absent until that transport exists, since a setting whose other value silently does nothing is exactly what the options mechanism was added to prevent. New sysop guide `docs/sysop/UPDATES.md`.

### Updating: Staging and Applying

- **A release can now be fetched, proved and landed on an installation by one tool.** `node src/tools/update.js` resolves a release, downloads it, verifies its checksum before unpacking anything, reconstructs a development delta against its base stable, checks the result against the manifest, works out exactly what applying it would do, and with `--apply` does it. Without `--apply` it writes nothing to the installation.
- **This is half of the updater and says so.** It does not stop the BBS, install dependencies, migrate the database, run the release's declared upgrade steps, or restart anything, and it prints those as remaining work when it finishes rather than implying they are done. `setup/update.sh` is still the supported path for a normal update. New sysop guide `docs/sysop/UPDATING.md`.
- **What an update does to a file is now a value a sysop can read, not control flow in a shell script.** `buildApplyPlan` is pure and returns a decision and a reason per file, so a dry run is the same code path with the writes turned off. This is the module that can destroy somebody's work: `install.sh` expressed the same rules as a sequence of `rm -rf` and `cp` calls, which is why nobody noticed that its update mode deleted every sysop-added asset under `public/`.
- Each category is a claim about whose file it is. Code is ours: overwritten, and strays in those directories are deleted, because a module the new release does not know about is still importable. Overlay is ours to add to and theirs to extend. `public/css/custom.css` is theirs the moment it exists. Config is theirs once touched. Art is theirs. **Removal happens only in code directories**, since anywhere else a file we did not ship and do not ship now is the sysop's, and the general form of that rule is exactly the bug that deleted their door icons and branding.
- **Whether a sysop edited a config file is now answerable rather than guessed.** `update.sh` compares mtimes, which say when a file was written and nothing about whether it differs from what shipped, so it has to stop and ask about every data file. Each release ships a manifest of content hashes and leaves a copy in the installation, so "still exactly what the last release shipped" means nobody touched it and the update is safe to take. An install predating this machinery has no manifest and cannot answer the question, so it fails to conflict: their file is kept and they are told. Guessing the other way would overwrite edits nobody can recover.
- A category the code has no rule for also falls to conflict rather than being written over. The updater runs from the new release's tree onto an older install, so the categoriser in play may well predate a directory the release added, and "I do not know what this is" has to read as "leave it alone".
- **A development build is reconstructed from its base, never patched into place.** The delta is laid over a freshly extracted base in staging, pruned to the manifest so deletions travel, and verified before anything is applied. The case that forces this: a file changed in an earlier development build and put back in a later one appears in neither delta at its correct content, so patching leaves it silently wrong while every individual step looked right.
- Everything the apply overwrites or deletes is copied into a backup directory at its own relative path before anything is touched, and files are written to a temporary name and renamed into place so a process reading one during an update sees the old file or the new file and never half of one. A failed staging run cannot leave an installation half updated, because nothing outside the staging directory is written until the tree has been verified.
- Two bugs found while testing this against real artifacts, both of which would have compounded silently. The installation's own manifest was not being rewritten after an apply, so the next update would have compared config files against the previous release's hashes and reported every legitimately-changed file as a sysop edit, for ever. And the manifest was not recorded in the backup, so a rollback left the install claiming the release it had just backed out of, which is the one lie that makes the following update reason from the wrong hashes.
- The move rule is checked before anything is downloaded, not after. Refusing a release after fetching twenty megabytes would be rude and refusing after extraction would be worse. Naming a version explicitly still goes through the release index, because the one time somebody names a version by hand is when they are trying to get past something.

### Updating: The Handoff

- **An update can now be handed to the release being installed.** `--handoff` stages a release, then launches the **new** version's own updater as a detached process and returns. Two reasons. A process cannot replace its own files while running, so an update started from the running BBS has the thing doing the work also being the thing replaced; and applying an upgrade is version specific and is where the bugs are, so doing it with the new release's code means a release can ship a fixed updater and it takes effect for *that* upgrade rather than the one after. `--apply` still does it synchronously for a sysop at the console.
- Detachment is the load-bearing part, because `pm2 stop all` signals the whole process group and an updater launched without it dies with the thing it was updating, halfway through. Verified by SIGKILLing the launcher's entire process group immediately after the spawn and confirming the update still completed and the installation came out at the new version.
- **The contract between the launching release and the applying release is a JSON run file, not a command line.** One argument, `--run <path>`. Those two are different versions of this software and both will keep changing: a newer updater reading an older release's file defaults what is missing, an older one ignores what it does not recognise, and a positional argument list can do neither.
- Staging now lives inside the installation, under `.canectic-update/`. Not tidiness: `node_modules` resolves by walking up from a module's own directory and a release artifact ships none, so an updater staged in `/tmp` cannot import anything with a dependency, which includes `alogger`. The dot directory is not a shipped category, so nothing scans, replaces or backs it up. The updater's working directory is the installation, where `.env` and `node_modules` live; only its code comes from staging.
- A release cut before this existed ships no updater to hand off to. The launcher checks, refuses, and names `--apply` as the alternative rather than failing obscurely on spawn. That is not hypothetical, it is every release to date.
- **Progress is a durable file, not a database row.** The updater is replacing `src/`, which includes the database layer, and may be running while the BBS is stopped, so making the one record of what happened depend on Postgres would put it out of reach exactly when it is wanted. It lives under `logs/update/`, writes are atomic, and `node src/tools/update.js --status` reads it long after the run finished and the process that started it was replaced.
- A run refuses to report success over a failed or still-running phase. Reporting a half-applied tree as a successful update is the worst outcome available, because the files are on disk, the processes are down, and the only record says it went fine. "Never reached" and "deliberately not done" are also kept distinct: this updater performs four of the ten phases and records the other six as skipped with the reason and the command to run by hand, so the run reads as incomplete on purpose rather than as stuck.

### Updating: The Whole Sequence

- **An update now does the whole job.** Stops the BBS, replaces the files, installs dependencies, dumps the database, migrates it, runs the release's automatic upgrade steps, and starts the BBS again, with each phase recorded as it happens. Anything it skips it names, along with the command the sysop now owes. `node src/tools/update.js --handoff`, or the Update button on `/admin/update`.
- **One implementation of the phases, used by both ways in.** `--apply` runs them in process and the detached updater runs them after a handoff, through the same module. Two programs that both claim to apply an update is the exact shape that let `install.sh` and `update.sh` drift until one of them deleted every sysop-added asset under `public/`, and there was no reason to build it a second time here.
- The file backup happens before the processes are stopped, since shipped files do not change while the BBS runs and there is no reason to pay downtime for it. The database dump happens after the stop and immediately before the migration, because it exists to protect the migration: taken any earlier it would not contain the writes in between, and taken before the stop that window would be as long as the dump itself.
- **A database dump is taken by default and can be declined.** Free space is checked against the actual database size first, so it fails before starting rather than halfway through leaving a truncated file that looks like a backup. Requiring one was rejected: a hub whose message base outgrows its free disk would then be unable to update at all. Warning only was rejected too, because the one time it matters there would be nothing to restore from.
- **A failure partway through rolls the files back, but only while that is still the right thing to do.** Up to and including the dependency install the only thing that changed is files, so the backup goes back and the BBS is started again. From the schema phase onwards it does not: old code over a migrated database is a worse state than the failure, so the update stops, says where the backup and the dump are, and leaves the decision to a person. The list of phases on the safe side is written out rather than derived from the order, because a phase drifting across that line is silent and only shows up during a failure.
- A failure that stopped the BBS starts it again, and says so. A board left down by a failure partway through is its own problem, separate from whatever failed.
- `dbmigrations.js` does the declarative pass and the migration ledger in one invocation, so the `migrations` phase is recorded as skipped with that as the reason rather than marked done. Marking it done would imply a second thing happened. It also means `dbmigrations` is no longer a declared upgrade step: the schema phase is structural and runs on every update, while steps are for release-specific one-offs.
- Process control is `update_process_control`, `update_stop_command` and `update_start_command`. A bare `pm2` is resolved next to the running Node before PATH, reusing the worker watchdog's helper, because under nvm the supervisor's PATH may never have held the version the BBS is running on. **Starting from the ecosystem file starts every process in it**, including one deliberately stopped, which is a known consequence of the simple option; the pm2 state is recorded so `--status` shows what was running beforehand.
- **Stable release artifacts are now cached, so a development update does not re-fetch its base every time.** A delta is always one hop against the stable it names, and a sysop tracking development needs that same tarball for every build cut on it. The cache keeps two by default and never evicts the base the installed version deltas against, nor lets protecting it consume the budget. A cached base is re-verified against its checksum on every single use and discarded if it fails: a local file is no more trustworthy than a downloaded one, it can rot on disk, and it is the base everything else is rebuilt from, so trusting it would silently produce a tree that passes its own manifest check while not being the release.
- **Everything the updater keeps now has one home and three lifetimes.** `.canectic-update/staging/` goes with each update, `base/` survives them, `backup/` lasts until reclaimed. Backups moved here from `logs/update/`, which now holds only the record: small, readable and worth keeping for ever, against bytes that are large and reclaimable. `/admin/update` shows the size of each and what deleting it costs, so "I need that space back" has an answer that is not guesswork.
- **Preflight runs before an update is offered, not after it has started.** Several of its checks are only answerable while the board is up: once the processes are stopped, nobody is online and nothing is in flight, and asking then is asking a question the asking has already changed. So it runs in the gateway with the board running, and the updater re-checks only the cheap invariants it can still see for itself. Blocking is reserved for things that make the update fail; **connected callers only warn**, because whether three people mid-door is a reason to wait is the sysop's call, and a preflight that refused on judgement calls is one they learn to bypass. Free space that cannot be measured warns rather than blocking, since blocking would make every filesystem without `statfs` un-updatable.
- **`/admin/update` has an Update button**, gated on preflight passing and on no run already live, with a confirmation that says plainly what it will do and how many users it will disconnect. The ordering is the trick: check, respond, and only then stage and hand off. The gateway is about to spawn something that stops the gateway, so the response has to be gone first, and the page reports afterwards from the run file rather than from the connection it was serving on. The run record exists from the moment the button is pressed, so a failure during staging shows up on the page instead of looking like nothing happened.

### Installing: One Command

- **A new sysop now runs one script and nothing else.** `setup/bootstrap.sh` resolves a release, downloads it, verifies its checksum before unpacking anything, extracts it, and hands off to that release's own installer. No `git clone`, and no source directory to look after afterwards. The old shape had a second copy of the software whose only purpose was to install the first, which could be stale, on the wrong branch or at an untagged commit with nothing checking.
- **Install is update from nothing, and that is now literal.** The file placement is the updater's own planner against an empty directory, so every file comes out as new and the rules that protect a sysop's work on an update simply have nothing to protect. There is no second copier. The first one was `install.sh`, and it drifted from `update.sh` until it deleted every sysop-added asset under `public/`. The phase vocabulary is shared too: an install skips backup because there is nothing to preserve and stop because nothing is running, while an update skips the .env phase because that file is the sysop's.
- **Fix, found by the first end-to-end run: the installer could not run on a machine with no dependencies.** It failed on `Cannot find package 'luxon'` before doing anything. Obvious in hindsight and easy to miss in development, where `node_modules` is always there: a fresh machine has an extracted release and nothing else, so `npm install` is something the installer RUNS and therefore cannot be something it needs. `updateApply` lost its logging import and the command helpers moved out of the update runner, which reaches `appConfig` and so `dotenv`. A test now walks the installer's import graph and fails on anything that is not a Node builtin or one of our own files, because this is exactly the kind of rule that holds until somebody adds one convenient import.
- **Runtime directories are now created on updates as well as installs.** A release ships no empty directories, because an empty directory is not a file, so the FTN spool, the logs and the art tree have to be made by something. That something was a block of `mkdir` calls in `install.sh` which an update never ran, so a release that starts writing somewhere new worked on a fresh install and failed on every upgraded one, at the moment the feature was first used rather than at update time.
- `.env` is written once from the shipped template with the values the installer was given, at mode 600 because it holds the database password, and is never rewritten: a directory that already has one belongs to somebody who set it up. A password is never defaulted or generated, since a credential nobody was told about in a file nobody looked at is worse than being asked for one.
- Installing over an existing installation is refused, naming the version found and printing the updater command instead, because it would treat every one of the sysop's files as new. `--force` overrides it.
- Automation stops where it stops being honest. The PostgreSQL role and database need `sudo -u postgres`, which is restricted on plenty of hosts and absent on managed Postgres, so `--create-database` runs the script that already handles that properly and without it the command is printed. Everything after the credentials exist is automated. A failed install is deliberately not rolled back: there was nothing underneath, so deleting the directory and starting again is simpler and safer than unpicking it, and the run says so.
- A development build cannot be installed from nothing, since it is a delta against a stable release. The bootstrap refuses one and names the stable to install first, rather than reimplementing reconstruction that the updater already does and has tests for.
- **The documented path is verify, then run.** `INSTALL.md` leads with downloading the bootstrap and checking its published checksum; piping it into a shell is shown as the alternative rather than the headline. This audience cares about provenance and it costs one line. Signature checking is wired for when a key is published: a `SHA256SUMS.asc` that is present but unverifiable warns loudly, and its absence is not yet a refusal.

### Updating: Over a File Echo

- **Releases can now arrive down a file echo, with no outbound connection of any kind.** Set `update_check_transport` to `ftn` and point `update_stable_file_area` at the area carrying the release echo. This is how BBS software was distributed for twenty years, it works for a board with an FTN link and no outbound HTTP, and it does not depend on a web host being reachable. The echoes are `CANECTIC` for announcements, `CANECTIC_FILES` for stable and `CANECTIC_DEV` for development builds.
- Almost nothing new happens on this path, which is why it was built last. By the time a release is interesting the TIC tosser has received it, checked it against the TIC, hashed it and filed it, so detection is a database query and downloading is a copy. The directory source the updater already had was written to take a directory as well as a URL for exactly this.
- **A file echo carries files, not indexes, so the channel index is derived from what the area holds.** Each archive carries a `CANECTIC.ID` and its own metadata at its root, which is what those sidecars are for. An archive that cannot identify itself is **dropped rather than offered**: its migration list would be empty, an empty migration list clears every blocker in the move rule, and an unidentifiable file would then be presented as safe to install against a database it says nothing about. The filename is treated as a hint only, since it survives a distribution chain that may rename, truncate or uppercase it; uppercased names are normalised, because 8.3 habits are still alive in parts of the network.
- **What FTN integrity guarantees is now written down rather than assumed.** The TIC's CRC-32, checked on arrival, and the SHA-256 Canectic computes and stores both prove a file has not changed since it got here. Neither proves it is the file that was built and published. So the locally computed hash is never put in the field that means "published checksum", and staging a release without one requires the caller to say it accepts that: refusing outright would make the transport useless, and skipping quietly would make the HTTP path a lie. The manifest end-state check runs either way, so a corrupted or truncated archive is still caught before anything is applied.
- Metadata that is **absent** is normal on a file echo, because two TIC'd files travel independently and one can be lost; the copy inside the archive covers it. Metadata that is **present and corrupt** stops the update instead, because that is somebody telling you something is wrong and quietly using a different copy would hide it. The two are told apart by a flag on the error rather than by catching everything, which is the difference between a fallback and a swallow.
- Publishing stays by hand, consistent with the release script: the artifact goes into a file area and the existing TIC machinery distributes it.

### Schema and Setup

- **One-time database migrations are now recorded, so they run once and can be reasoned about.** The declarative schema in `db/schema` converges on a shape no matter what state it finds, which is exactly why it cannot express an event: "renumber every QWK conference once" is not a shape. Asking a converging system to perform an event had produced four different answers to the same question, one per case (schema sniffing for the menu layout, a marker row in `settings` for the MSGID split, nothing at all for `qwkConfRenumber`, and an unanswerable question for `allow_netmail_relay`). There is now a `schema_migrations` table, a `db/migrations/` directory of ordered `NNNN-slug.js` modules, and a runner in `src/maintenance/migrationLedger.js`. Once a migration is recorded it is never considered again.
- Migrations declare a phase, `pre` or `post` relative to the declarative schema pass. The `pre` phase is not a nicety: the menu layout migration has to read `entries_x_offset` before that column is dropped, and running it afterwards would convert data that is already gone.
- A migration can be manual (`automatic: false`), meaning it is reported with instructions and never run. That is how the MSGID tuple split is carried now: its predicate full scans every per-area message table, so a sysop chooses when to pay for it, and `maintenance.js --fix-msgids` records the completion in the ledger when it finishes. A system that ran the repair before the ledger existed is recognised by its old `settings` marker and recorded as not needing it, so nobody is told to redo expensive work they have already done.
- One row per attempt rather than one per migration, with no unique constraint on the id, following `mailer_sessions`: a failed attempt is the history worth reading later. `failed` is deliberately not a terminal outcome, so fixing the cause and running again picks up exactly where it stopped, and everything that already succeeded is left alone.
- A fresh database records every migration as never needed instead of running it, since a database created by this release is born current and has no legacy data to repair. That is decided from whether the `users` table existed before the run, checked before anything creates tables. Getting it wrong in the other direction is the dangerous one: an existing install treated as fresh would skip every repair it actually needed, in silence.
- Migrations run from `dbmigrations.js`, which is a CLI invoked during an update, and not at gateway startup. A migration that fails fails an update and cannot stop the BBS from booting. The run stops at the first failure rather than continuing, because a later migration may depend on an earlier one and carrying on is how a half-migrated database happens.
- **The QWK conference renumber is now a migration rather than an upgrade step to remember.** It was documented as "after pulling this release and before restarting, run `node src/tools/qwkConfRenumber.js` once". Leaving it undone is not cosmetic: a group with no `qwk_conf_start` cannot have a new area created in it at all, because `nextConfNumberInGroup` throws and the sysop sees a failed area creation pointing at a tool they were supposed to have run. It now runs automatically as `0003-qwk-conference-blocks`, in default mode only.
- Default mode is what made that safe to automate: it preserves every conference block already assigned and fills only the gaps, and inside a block it keeps each area at the offset it already holds. An area that is already correct is never renumbered, because every renumber invalidates a conference list somebody is holding in a mail reader. `--force`, which discards and repacks everything, stays a deliberate choice made at the command line and is never run by the migration.
- A group holding more areas than `qwk_group_stride` allows now stops the update with the group named, rather than exiting 1 from a tool a sysop may not have been watching. That is a real decision for them (raise the stride or split the group) and half a renumber is worse than none.

## Bug fixes

### Configuration

- **Tier 1 is now the `.env` file read from disk, not `process.env`.** Editing `.env` and restarting had no effect, with no error and no warning. Two behaviours combine: `pm2 save` snapshots the environment into `dump.pm2` per app and replays it into each child on restart or resurrect, and `dotenv.config()` then declines to correct it because it does not overwrite a key already present in `process.env`. The contract was written about a file and implemented against an ambient environment. Precedence is now: in the file and ambient, the file wins and the disagreement is reported; file only, the file; ambient only, ambient, so one-off command-line overrides still work; neither, the database and then the default. Bootstrap keys keep ambient precedence, since they are needed before the file can be located and `PROCESS_MODE=embedded node bin/gateway.js` is supported. Divergence surfaces three ways: a per-key warning at load and reload naming both values and giving the pm2 remedy, `appConfig.getEnvDivergence()`, and a banner plus badge tooltip on `/admin/config`. Values for keys matching pass, secret, token or credential are redacted in all three.
- **Fix: the source badge on `/admin/config` claimed the database for settings nobody had ever touched.** Any row present in `settings` was reported as coming from the database, and since every default is seeded there on first run, that was very nearly every key: on a real install, 122 of 158 keys were sitting at exactly what the release ships while the page said otherwise. A stored value now reads as coming from the database when a sysop set it, or when what is stored differs from what this release ships. The second half matters because a seeded value goes stale when a default changes between releases, and that stored value is still the one taking effect, so reporting it as the default would be wrong in the other direction.
- **Fix: an upgraded install reported the version it was first installed at, not the one it was running.** `currentversion` is derived from `package.json`, but `configStore` seeds defaults with `ON CONFLICT DO NOTHING`, so the row is written once on first run and never refreshed. On the development box it was seeded on 2026-03-20 saying `0.1a` and still said `0.1a` six months later while the code was `0.9.5a`. Everything that read the config path reported the stale value: the `@VR@` art code, the terminal system information display, and the `@PID` kludge on every FTN message posted. Any install that has been upgraded rather than freshly installed has the same problem.
- `systeminfo.softwareVersion()` now reads `package.json` first and treats the config value as a fallback for the case where that file cannot be read. A version is not a preference: setting it does not change what is running, it only makes the system misreport itself to its users and its peers. Migration `0005-refresh-stale-version` corrects the stored row as well, since `/admin/config` displays it, and touches it only when the sysop never set it deliberately, which is the first use of the provenance the previous change made available.
- **Fix: the binkp and EMSI mailers announced `Canectic BBS Mailer/0.1` to every peer.** `PRODUCT_VERSION` was hardcoded and had never been updated, so every FTN system this software has ever called was told it was running version 0.1. Both now take the version from `systeminfo` at the point the banner is built rather than at import, since config is not loaded when those modules are first imported.
- The version had six readers going three different ways with three different fallbacks (`0.0.0`, `0.1a`, and the hardcoded `0.1`). `artCodes` and `messages.js` each called `appConfig` directly rather than going through `systeminfo`, and `dbmigrations` read `package.json` itself, twice. Everything now goes through `systeminfo`, which also gained `versionInfo()` for callers that compare rather than print, and `canonicalVersion()` so a stray `v` prefix or a retired spelling never reaches another system. A test asserts that nothing outside `configDefaults` and `systeminfo` reads the version for itself.

### Message Bases: Import, Retention and Moderation

- Both parsers now stream. `iterateJAM` and `iterateSMB` are generators yielding one message at a time, reading each body from a file descriptor rather than holding the whole text file plus every decoded message in memory. This was not theoretical: the first bulk run exhausted the worker heap twice at around 5,000 messages. A 393 MB base with 100,000 messages now peaks at 4 MB of heap, and a real 106,000 message import ran at 157 MB RSS.
- Fix: SMB import stored the full `"address serial"` MSGID string in `msg_id` and left `msg_orig_addr` empty, so a message imported from SMB would not dupe-match the same message arriving later over FTN. It also never set `source_network_id`, leaving imported history eligible to be tossed back out to peers. Both now match what `ftnToDb` does.
- Fix: `statSMB` and `statJAM` read into a pre-zeroed fixed buffer and handed the whole allocation to the parser, so a half-copied file looked like a valid empty base.
- Fix: both push paths, message and file, did `pushDefaultsToAreas(shortcode, fields || ['all'])`. The form posts one entry per ticked checkbox, so unticking everything sent no fields, fell through to `['all']`, and pushed every setting. With retention in the list that could silently disable pruning across a whole group in one click. The routes now stop with a warning and both models treat an explicitly empty array as push-nothing.
- Fix: the lazy-load endpoints built their JSON message shape by hand and left out `uuid`, so messages appended by "load more" carried a delete control addressing nothing while the first thirty on the page worked. Both endpoints now go through `messages.messageForClient`, one tested definition of the wire shape.
- Fix: `buildMoveTargets` resolved the networked flag with a query per area, so a board carrying two hundred areas ran two hundred queries on every thread page.
- **Fix: message dates that cannot be true are rejected at both ingest points.** Chasing 2060 dates in an imported COOKING base: all ten were from one author, all carried tz -0400, their MSGIDs decoded to July 2024, and every one was congruent to 16 seconds mod 60, so systematic corruption at the source rather than a wrong clock. Faithfully importing bad data is still a problem, because the damage is downstream and silent: the area's `last_message` became 2060-10-14, which pins it to the top of the recently-active sort permanently, keeps it inside every retention window so it is never pruned, and renders as a plausible "Oct 14" in the list column. `sanitiseMessageDate` now falls back to the receive time for a date more than two days ahead, before 1980, or unparseable, and logs why. Applied in `echomail.ftnToDb` and `smbImport`. The two-day tolerance is deliberate: clock skew of minutes or hours between FTN systems is routine, years ahead is not. This guards new arrivals only; rows already stored keep their bad dates.

### Message Networking: Netmail Relay

- **Fix: relayed netmail was claiming the wrong origin in both directions.** A netmail carries two "from" addresses answering different questions: the message header says who wrote it, the packet header says who is handing the packet over. Those are the same address for mail we originated and different for transit, and they were backwards. `TossOutboundNetmail` stamped our address over the message header regardless of `transport_data.relayed`, while `WritePkts` derived the packet header from the INTL kludge, which on transit mail names the original endpoints. So a relayed netmail went out claiming to be written by us and sent by the originator, with replies going back to the wrong system. `resolveOutboundSource` now answers both questions in one tested place, and `WritePkts` groups on an explicit `PacketSource` rather than guessing from INTL.
- **Fix: no Via line was ever written, so an enabled relay had no loop protection at all.** Two systems routing to each other would pass the same message back and forth until a sysop noticed. `relayNetmail` now refuses a message that has already been through any of our addresses and stamps its own hop before queueing. Matching is on the bare address and case insensitive, because a system may write itself into a chain with a domain on one hop and without it on the next, and a loop check that misses is worse than none since it reads as protection.
- Fix: the inbound Via parser kept two tokens and dropped the rest, losing the timestamp or the software from every line it read depending on whether the writer used the optional `@`. A truncated chain still relays and still looks like a path, so nothing complained. The raw line is now kept so another system's hop survives a relay verbatim.

### Message Networking: AreaFix, FileFix and Echolists

- **Fix: deleting an area left echolist entries pointing at it.** `removeArea` cleaned up the area record, its two backing tables, its peer subscriptions and its network_areas mapping, and left `local_area_id` on `network_echolist_areas` alone. That field is what makes an areatag read as locally carried throughout the admin UI. The daily reconciliation would eventually clear it, but only for active entries and only by matching areatag, so an inactive entry kept the pointer for ever and every entry kept it until the next daily run. The window is the part that bites: area ids come from a sequence, so a stale pointer does not stay visibly broken, it eventually names whichever area took the id, and nothing in the UI can tell that from the truth. Both `removeArea` functions now clear by id at the point of deletion, which needs no areatag match and covers inactive rows, and both reconciliations now clear any pointer whose area no longer exists at all, which repairs databases already carrying dangles.
- Fix: `removeArea` reported success when the final delete failed. `postgres.write` reports a failure in its return value rather than throwing, so the `try/catch` around it could never fire: the area stayed and the caller was told it had gone. Both the message and file versions now check the returned error, which is also what makes the echolist clearing above meaningful, since a cleanup that cannot be seen to fail is not a cleanup.

### Message Networking: FTN Tosser and Packet Fixes

- **Fix: a hub was suppressing nearly all forwarded echomail.** `getOutboundForConnection` skipped any message whose `source_network_id` matched the connection's network, on the reasoning that a message should not go back to the network it came from. That conflates the network with the node: a hub receives from its uplink on network N and must forward to its downlinks, which are also on network N. That is what echomail distribution is. Since `handleInboundEchoMessage` stamps `source_network_id` on every inbound message, the filter matched nearly everything: on the reporting system, 127 of 129 candidate messages for a downlink were suppressed, and the two survivors were locally posted. Only mail the sysop typed themselves was leaving the system. Not re-sending to the node a message came from was already covered twice, by the explicit source-address check and by full SEEN-BY parsing per FTS-0004. With the filter gone, the same 129 candidates break down as 126 stopped because that peer sent them, 2 by SEEN-BY, 1 sendable. The one useful job the filter was doing, keeping imported history from being re-exported, is now an explicit `imported` column on the area tables.
- **Fix: message area creation was broken outright.** Appending the `imported` column to `src/templates/msgTable.conf` left the file with a trailing newline; `getColumnsFromFile` split on newline with no filtering, so the trailing newline became an empty column entry and `CREATE TABLE` emitted `", )"`. Any new message area created would fail after writing its row, and `newArea` rolls the row back, so the symptom was a create reporting failure with a half-made area. `getColumnsFromFile` now drops blank lines so the format is not one stray keystroke from breaking area creation again.
- **Fix: the import seal could jump over mail that arrived mid-import**, which was the originally reported symptom. `advanceOutboundIdxForArea` sealed `msg_idx` to `MAX(id)` as of the seal rather than to the last row the import wrote. Inbound tossing runs on the toss worker while a bulk import runs on the maintenance worker, so ordinary mail lands interleaved with imported rows, and sealing to `MAX(id)` moved `msg_idx` past that mail so it was never sent downstream, silently. During a long bulk import that is the expected condition, not a rare race. The seal now stops one short of the oldest non-imported row above the floor.
- **Fix: the netmail writer stamped no packet password.** Two writers produce packets: echomail goes through `WritePktToNode`, which reads the peer's own `packet_password` from `connection_data`, while netmail went through `WritePkts`, which read the global `PacketPwd` key and nothing else. A sysop who set a packet password on a link therefore got authenticated echomail and netmail with eight zero bytes where the password belongs. Found from two AreaFix requests an uplink returned: the password was correctly in the subject, which is where AreaFix wants it, and the packet header field was empty, which is what the uplink was actually rejecting. The peer lookup is keyed on the packet destination rather than the message destination, since that is the system we hand the packet to and therefore whose password applies, which also means relayed mail gets the hop's password. Address matching drops a 5D domain suffix and a trailing `.0`. The global key stays as the fallback for links with none of their own. The AreaFix/FileFix/Ping response path was also sending unauthenticated replies and had stopped reporting queued responses because it was not awaiting the now-async writer. A packet going out with no password at all is now logged, which is worth knowing before the far end tells you.
- **Fix: the inbound backstop only ever noticed literal `.pkt` files.** `TossInbound` also processes arcmail bundles, matched on the FTS-5000 filename pattern, so a bundle sitting in the inbound triggered nothing. In normal operation that was invisible, because the mailer enqueues a toss itself the moment a binkp session receives files. It only shows when that enqueue did not happen: a worker that was down, a restart between receipt and enqueue, a bundle put there by hand or recovered from a filebox. Those are exactly the cases a backstop exists for, and mail could sit unclaimed indefinitely with nothing reporting it. Both paths now share `ftnTosser.isTossableInboundFile` so they cannot drift apart again, and the scan names the file that triggered it.
- **Fix: the inbound scanner threw a stack trace on every pass** if the inbound held a subdirectory, which sysops routinely keep (`ftn/in/Old` is the usual one). The type sniffer read every directory entry with `readFile`, so each pass threw EISDIR and dumped a trace through `console.error`, outside the log bus and outside the configured level. At the inbound scan interval that is a trace every few minutes for ever, which on a live hub buried the lines that mattered. It now stats first and treats anything that is not a regular file as "not ours". It also sniffs with `fileTypeFromFile` rather than reading the whole file: magic numbers live in the first few bytes, but an inbound holding arcmail bundles or TIC attachments was being loaded into memory in full, every file, on every scan.
- **Fix: a colon-form INTL kludge crashed the whole packet read.** `processMessageText` threw "Assignment to constant variable" on any `INTL: <dest> <orig>` control line, because the dedicated `INTL` branch reassigned consts declared above the switch and ES modules are strict mode, so it failed the whole packet rather than one message. The branch was wrong in three further ways even without the throw. Removing it is the fix: the default branch already parses both forms correctly.

### Mailer

- **Fix: a peer configured to poll every 240 minutes was being called every minute.** The poll schedule was correct and had nothing to do with it. The BSO scanner decides a node has mail from the filename, never the contents, which is fine for packets and wrong for flow files, which are a list of things to send and can end up listing nothing. A spent flow file therefore read as pending work for ever: the scanner triggered a session, the session skipped every line, nothing was sent, nothing deleted the file, and it happened again on the next scan. At the default 60 second scan interval that is one connection a minute indefinitely, and `poll_interval` is not involved because this path calls `_connectToPeer` directly. Two ways a flow file gets into that state: every line already marked `~`, because the delete was gated on a line changing during that call, or lines naming files that no longer exist, which were skipped silently and left unmarked for ever. `src/utils/floFile.js` now owns this: `pruneFlowFile()` marks vanished lines and deletes an exhausted file, called from the scanner before it counts an address as having mail and from both outbound list builders so the tidy-up does not depend on any one caller running. `pendingCount()` is the honest answer to whether a node has mail, as against whether a flow file exists.
- **Fix: connect backoff was doing nothing whenever mail was waiting.** The guard was in `pollConnection()` only, and the BSO scanner calls `_connectToPeer` directly, so a peer refusing connections was retried every scan interval. The guard now lives in `_connectToPeer` itself, which every outbound path comes through; `triggerPoll` passes `force: true`, because a sysop pressing the poll button has said what they want. The scanner keeps its own check so it can report backoff skips in the scan summary, but enforcement no longer depends on any caller remembering.
- Fix: nodelist-routed addresses had no backoff of any kind, which is the worse half of that. Backoff state lives in a peer connection's `connection_data` and these have no peer row, so nothing counted their failures and nothing limited the retries: a dead route cost a connection a minute indefinitely. The manager now keeps an in-memory map for them with the same doubling and cap, fed by both the connect error and the session end and cleared when a session completes. In memory rather than persisted because these are transient routes rather than configured links, and `mailer_sessions` is the durable record.
- **Fix: a poll interval changed in the admin UI sat in the database doing nothing until the next gateway restart.** `updateConnectionSchedule` existed, its doc comment said to call it from the admin routes, and nothing did. Schedules were only ever written by `registerSchedules()` at startup, while the peer page showed the new value the whole time. The same gap left orphans behind: registration skips connections whose polling is disabled rather than clearing them, and nothing removed a schedule when a connection was deleted, so both kept firing indefinitely. The create, update and delete routes now maintain schedules directly, and `updateConnectionSchedule` takes the connection row rather than loose fields so a caller cannot pass one with polling disabled and get a schedule anyway.

### Worker Health and Queue Diagnostics

- **A hub went four days without tossing while pm2 reported the worker online for the entire period.** The process was alive, its event loop was turning, and every concurrency slot was held by a job that would never return. The worker owns both the toss and maintenance queues and nothing else drains them, so losing it stops all message tossing, all TIC processing and every maintenance sweep while the web and the terminal carry on normally, which is why it goes unnoticed. There are three failure modes and only the first is the one a supervisor sees: the process exits (pm2 restarts it), the process is alive with its consumer closed (nothing), and the process is alive with a job that never returns (nothing). BullMQ's stalled-job detection cannot cover the third, because a job parked on an await renews its lock exactly like a healthy one; at the default toss concurrency of three, three of those and the queue is stopped with nothing logged.
- Both queue processors are now wrapped in a timeout, so a job past its limit rejects, BullMQ retries it, and the slot comes back. `toss_job_timeout` 30 minutes, `maintenance_job_timeout` 60 minutes (higher because imports and batch subscribes legitimately run long), 0 disables.
- pm2 config: the worker had `max_restarts` 15 with a flat 2s delay and a 3s `min_uptime`, so a worker exiting at startup because PostgreSQL or Redis was briefly away burned all fifteen restarts inside a minute and pm2 then left it stopped for good. Exponential backoff and a 30s `min_uptime` instead.
- **Orphan job schedules are now removed automatically at gateway startup.** Registration rebuilds the whole managed set from the database on every start, and anything in a managed family it did not just write has no row behind it: a connection that was deleted, or one whose polling was turned off, which registration skips rather than clears. Those kept firing their job for ever, once per interval, and the only way to find them was to run the diagnostic by hand. Five were live on the development box, two of them for connections that had been deleted outright. The sweep covers mailer polls, QWK and NNTP pull/push, timed events and coordinator stub generation, and is confined to those families by an explicit allowlist, so the fixed daily maintenance schedules can never be candidates however the expected set is built. It runs only after a registration pass that completed, since pruning against a half-built list would delete live schedules. `src/tools/schedules.js --prune` still exists for clearing them without a restart.
- `src/tools/schedules.js` now knows about timed event and coordinator segment schedules, which it did not previously list as expected at all. It shares the orphan rule with registration so the two cannot disagree about what is managed, and it compares cron patterns as well as intervals: a timed event registered with the wrong pattern used to read as matching, because both sides were comparing an interval that neither had. `--sync` deliberately skips those two families, since their job payloads differ and gateway startup rewrites them anyway.

### Admin Panel

- **Fix: file areas could not be created or edited through the web at all.** The modal opened, every field worked, and there was nothing to save with. The mixin conversion above left the submit button behind in each caller, so all three forms rendered without one. That conversion was verified by diffing the set of element ids rendered before and after, and a submit input has no id, so the check passed while the button was gone. The button now lives in the mixin, keyed on mode, so a caller cannot forget it, and it sits outside the tab content deliberately: inside, it would appear only while one tab was open, which looks the same as the bug from the other two. `tests/adminFormSubmit.test.js` renders the real templates and asserts that every admin form has something to submit it with.
- **Fix: every refused admin request returned 500 instead of 403.** `requireAdmin` rendered `admin/unauthorized`, and there was no such template. The render threw, Express caught it, and the caller got a server error, while the alog line the guard had already written said the request was refused. The logs and the response disagreed on every admin route using the middleware, and a refusal looked like a crash. The page now exists, with the same guard chain every other admin view uses: the unauthorized panel for a logged-in user without access, and the login form for a caller with no session, since a refusal to someone not logged in should offer them the way in. A refusal to a caller that asked for JSON (a `.json` path, `X-Requested-With`, or an Accept header naming JSON and not HTML) now answers JSON, because a JSON caller handed an HTML error page reports a parse error rather than the 403 that actually happened. `tests/adminRenderTargets.test.js` checks every literal `res.render()` target in `src/routes` against the views directory, which is the only way a missing template on an error path is caught before a user finds it.
- Post As is now on the new-group modal for message groups. The backend already handled it; the form just never sent the field, so a group created there silently took the `username` default and could only be changed after opening the group.

### Web and Terminal

- **Fix: an older browser window could be sent back to the call flow on every page, endlessly**, while a newer window on the same account was fine. `last_callflow_at` is cached on the session so the trigger check does not query the database per request, and that cache has no expiry. Three things had to hold for it to be endless and all three did. The username index dropped the session: `session_index:<username>` was written once at login with an expiry of twice `session_ttl` and never refreshed, while the session hash was renewed on every page view, so a Remember Me session outlived its own index entry by days. That also silently broke every other broadcast, including security level changes and config pushes, just less visibly. Completion broadcast to the index and fell back to the current session only when the broadcast had updated nothing at all, so a user with any newer session got a non-zero count and no fallback. And nothing re-read the authoritative value, because the lazy database lookup is gated on a flag set once and never cleared. All three are fixed: the index is re-added on session renew, completion writes the current session first and unconditionally, and `GET /callflow` reconciles its cached timestamp against the database on load.
- **Fix: art rendering could stall the terminal outright.** `@TC@`, `@TU@` and `@ON@` reach PostgreSQL or Redis and `processArtCodes` runs on every menu redraw. The resolvers had try/catch and were described as graceful fallback, but a catch only handles rejection: both clients retry internally, so an outage produces a hang, which nothing caught. It was not only an outage problem either, since every redraw ran `COUNT(*)` over calls and users plus an `sMembers` and one Redis get per online user, paid continuously while healthy. `resolveStat` now caches per code with a TTL and races a refresh against `art_stat_timeout_ms` (new key, default 1500), returning the last known value on timeout while leaving the refresh running to fill the cache for the next render. Once a render gives up on a particular refresh, later renders do not wait on it again: measured with Redis down, 1502ms once and then 0ms. Failures no longer overwrite good data, where previously a failed COUNT cached '0' as though it were true. `@ON@` splits into a cached web presence count and a terminal node count computed locally, so a Redis outage still reports connected terminal users instead of zero.

### Release Engineering

- Fix: the release script would build a delta against whatever manifest it was pointed at, without checking it described the tree the metadata names. The version and the `base` field are both derived from the version string, so they agree with each other whichever manifest was loaded, and a `--base-manifest` aimed at the wrong place produced a published delta that reconstructs into a tree no release corresponds to. The manifest states its own version, so the check is one comparison.

### Updating: The Handoff

- **Fix: the update tool reported the version of the tree it was running from rather than the tree it was about to modify.** Identical whenever `--target` is the current directory, which is exactly what anyone testing by hand would use, and wrong for every other case: the move rule was comparing the wrong system's migrations and upgrade floor. Reading an installation is now its own module with a target argument, and it also answers the two-manifest question the data-file rule depends on.
- **Fix: naming `--version` explicitly skipped the move rule.** The release was taken at the caller's word instead of being looked up, so the one time somebody names a version by hand, which is when they are trying to get past something, was the one time nothing checked. It now always resolves through the release index.
- **Fix: the tool would hang indefinitely on a stopped database.** The pg pool retries internally, so asking the migration ledger a question on an unreachable database never returns. It is now bounded, and an unreadable ledger comes back as "unknown" rather than as an empty list, because treating "we do not know" as "nothing applied" would clear every migration blocker and wave through precisely the move the rule exists to stop. ### Schema and Setup

- `message_groups.post_as` was created by a runtime `ALTER TABLE ... IF NOT EXISTS` at gateway startup rather than declared in `db/schema`, so `dbmigrations` neither knew about it nor reported it. It was not alone: two `ensureSortOrder` functions called from `bin/gateway.js` on every boot issued eleven such ALTERs between them, six redundant and five genuinely missing. All five are now declared with the same types and defaults, and both functions are removed. Schema lives in one place.
- Dropped the `netmail_bad` placeholder, which was listed in `tablenames.conf` with a zero-byte column definition file, so `dbmigrations` reported "no column definitions" on every run and never created the table. Bad inbound netmail is already handled by `pm_undeliverable`, which carries a full review workflow. The schema test that let this sit unnoticed skipped empty `.conf` files as valid placeholders; that skip is now an assertion, so a table listed with no column definitions fails the suite instead of producing a migration error on every run.
- `setup/create_pg_db_user.sh` creates the database as UTF8 explicitly (see upgrade notes), and warns when it adopts a pre-existing database that is not. `setup/convert_db_encoding.sh` is new. README gains a manual database creation section, because the script needs `sudo -u postgres psql` and fails where that is restricted; it covers the three things that actually bite, which are the missing ENCODING clause, PostgreSQL 15+ revoking default public schema grants (the cause of permission errors from `dbmigrations.js`), and peer authentication.
- **Migrations and startup schema maintenance are roughly ten times faster.** Both the static tables and the per-area message tables asked `information_schema` whether each column existed, one round trip per column. A message area has two backing tables of about 28 columns each, so maintaining one area cost roughly 114 queries, and `tablenames.conf` carries about 127 more tables on top. Measured on a 31 area development box: 6.9 seconds for the area tables and 3.2 for the static ones, paid on every `dbmigrations.js` run and every process that calls it, almost always to establish that nothing needed doing. On a hub with several hundred areas that is minutes per update. Both paths now read a table's columns in one query and compare in memory, and share the reader so they cannot drift. Same 31 areas afterwards: 0.47 seconds and 0.95. This was the other half of the slow update that the MSGID split fix addressed; that half is now done too.
- The two `ALTER TABLE ... ALTER COLUMN seen_by TYPE TEXT` statements that ran for every message area on every maintenance pass are now conditional on the column still being `varchar`. The template has said TEXT for a long time, so this was two `ACCESS EXCLUSIVE` locks per area per run to change nothing. The decision costs no extra query, since the column read above already carries the type. A failure to widen is now reported rather than discarded: `postgres.write` returns the error instead of throwing, so the old code could not tell a column it could not widen from one that did not need it.
- Fix: a column definition separated by a tab rather than a space could never be matched or added. The name was taken with `split(" ")[0]` and then had whitespace stripped, so `seen_by\tTEXT` produced the name `seen_byTEXT`. A definition with leading whitespace produced an empty name and was skipped in silence. Neither happens in a shipped definition file today, which is the only reason it went unnoticed; both are now parsed correctly and tested.
- Fix: a column definition with a capital letter would be re-added on every run, for ever. Postgres folds an unquoted identifier, so `MixedCase TEXT` creates a column named `mixedcase`, and the exact-match existence check never found it again: every migration emitted `ADD COLUMN MixedCase`, which failed, and the failure was one more error line in a long run. Column matching is now case-insensitive on both the add and the remove side.
- **Fix: `setup/install.sh` update mode deleted every sysop-added asset under `public/`.** It detected an existing installation and offered to update it, and its update path did a full `rm -rf` replace of each code directory with `public` still in that list. `setup/update.sh` had moved `public` into an overlay so door icons, collection images and custom branding survive an update, and added a skiplist so `public/css/custom.css` is seeded once and never overwritten. `install.sh` never received either change, so running it against a live board destroyed all of it, and the script invited that by detecting the mode itself and offering. It now refuses and points at `update.sh`, saying what that script preserves rather than only that it is different. Issue #44.
- The cause was two programs claiming to update, with duplicated directory categorisation that drifted when only one of them was changed. `do_update` and `merge_data_dir` are removed from `install.sh` rather than brought back into line, so there is no second copy left to drift. Installing is all that script does now.

### Bugfixes

- Fix: binkp sessions containing a file transfer were being logged as `failed` by binkd peers, which then re-queued every file they had just delivered — a redelivery loop, despite the data arriving and tossing correctly on our side. Root cause was a missing binkp/1.1 feature, not a teardown race. A binkp/1.1 session is a sequence of **batches**: each ends with an M_EOB from both sides, and the session ends only on a batch that carried nothing but those two M_EOBs. binkd counts every command frame in either direction as `msgs_in_batch` (data frames excluded, handshake excluded) and, when a batch closes with more than two, clears **both** EOB flags and opens another batch with a fresh M_EOB. Canectic treated the first mutual EOB as end-of-session and closed, leaving binkd with `remote_EOB == 0` at its post-loop check, so it logged `failed` and called `create_poll()` to restore the poll. Empty sessions land on exactly `msgs_in_batch == 2` and terminate after one exchange, which is why only sessions carrying a file ever failed and why the bug looked like a close-timing race. `_checkSessionEnd()` in `src/mailer/protocols/binkp.js` now mirrors binkd's accounting exactly: per-batch command-frame counter, both EOB flags cleared at a batch boundary, and the continuation M_EOB sent by the protocol itself. Verified against a binkd state-machine emulator transcribed from `protocol.c` — the same file session that produced `failed` before the change now produces `OK`.
- Fix: Synchronet BinkIt peers were being sent `M_ERR "Forced Shutdown"` at the end of every file session with us. BinkIt calls `reset_eob()` on each non-M_EOB frame it receives, so an M_GOT arriving after our M_EOB zeroed its `goteob` counter and its `close()` took the `if (!this.goteob)` branch. Two changes fix it: our M_EOB is now held until every M_GOT owed for the batch has been written, and the binkp/1.1 continuation batch above ends on a bare M_EOB with nothing following it. BinkIt sessions now close gracefully with no M_ERR.
- Fix: the mailer would deadlock against any peer that also waited for the remote M_EOB before sending its own (including another Canectic instance with nothing to exchange), holding the connection until the session timer fired. Our M_EOB is now sent as soon as the send queue drains, matching binkd, rather than waiting on the peer's.
- Fix: Bad echomail recovery ("Recover from bad echomail") was failing with `invalid input syntax for type integer: ""` for every held message. `recoverMessages` rebuilt the FTN message object without setting `Source`/`Destination` address strings; `echomail.ftnToDb` then evaluated `ftnMessage.Source ? ftnMessage.Source.split(":")[0] : ""` and inserted the empty string into the `source_zone`/`destination_zone` INTEGER columns. Fixed: recovery now restores `Source` and `Destination` from stored addresses and parses Zone/Net/Node from them. `ftnToDb` hardened to coerce all address integer columns via `toIntOrNull` and fall back to the integer `SourceZone`/`DestinationZone` fields when strings are absent. Schema gains `destination_address` on `echomail_bad` so future bad messages store the full destination for recovery fidelity. Run `dbmigrations.js` after update to add the column.
- Fix: Outbound FTN echomail `@REPLY` kludge was emitting only the parent's serial with no origin address, because the reply path from both the terminal msgEditor and the web flat/thread/admin reply modals was passing only the bare serial (`msg_id`) to `replyToThread`. `splitFullMsgid` on a bare serial correctly produced `{msg_orig_addr: '', msg_id: <serial>}`, which stored `reply_orig_addr` as empty; the outbound `dbToFtn` then joined empty-addr + serial back to just the serial for the kludge. Reworked the contract: callers now pass `formObj.reply_to_uuid` (the parent message's DB `uuid`) and `replyToThread` looks up `msg_id` / `msg_orig_addr` from the authoritative row in the area's msgs table, eliminating the client-assembled tuple string and the trust on whatever the form posted. Added a fallback to the thread root's `threadid` (full "ADDR SERIAL") when no parent uuid is provided (e.g. QWK REP imports that only match by subject). Web views (`messages/areas/flat.pug`, `thread.pug`, `admin/msgAreas/thread.pug`) updated: Reply buttons carry `data-bs-msguuid` and the hidden input is `reply_to_uuid`. The terminal msgEditor passes `this._replyToMsg.uuid`. `getMessages` / `getMessagesForThread` / `getMessagesForArea` SELECTs include `msg_orig_addr` + `reply_orig_addr` for display consistency. `@REPLY` kludges on new echomail/netmail replies are now FTS-0009 compliant.
- Fix: outbound netmail addressed through the 5D form of the SMTP/IMAP pseudo-TLD leaked the FTN domain into the `INTL` kludge. Sending to `user@21.1.100.fsxnet.ftn` stores `to_address` as `21:1/100@fsxnet`, which flowed unmodified into `msg.Destination` and then into `INTL 21:1/100@fsxnet <source>`, where FTS-0001 specifies bare `zone:net/node`. The damage was not limited to the kludge text: `WritePkts` parses the `INTL` value back apart to build its packet grouping keys and overwrites `message.Source` / `message.Destination` with what it finds, so a domain-bearing address also split packet groups and wrote the 5D string back into the message's own address fields. New `bareFtnAddress()` helper in `src/middleware/tossers/ftnTosser.js` strips the `@domain` suffix (preserving the point) and is applied to both halves of the `INTL` value at construction. 4D addressing was never affected. Note that network selection on outbound is still driven by the destination **zone** via `systemAddresses.resolveSourceForDestinationZone()`, not by the domain label, so the label remains informational for routing purposes.
- Fix: AreaFix and FileFix `+TAG` / `-TAG` / `%COMMAND` body parsing was splitting on `/\r?\n/`, which never matches in FTN messages. FTN message bodies use bare `\r` as the line delimiter (set in `ftnTosser.processMessageText` as `bodyLines.join('\r')`), so the entire body collapsed into a single line. The tear-line `startsWith('---')` guard never fired, the `+` branch swallowed everything after the tag (kludges, tear line, origin) into the areatag string, the SQL `UPPER(na.areatag) = $2` lookup missed, and the requester saw `  TAG\r--- TearLine: not found on this network` rendered as a visually-broken two-line response while no row was ever written to `peer_area_subscriptions`. Split now uses `/\r\n|\r|\n/` in both `src/models/areafix.js` and `src/models/filefix.js`.
- Fix: Nodelist auto-scan was hardcoded to only match files literally starting with `NODELIST.`, silently skipping every network that uses a different naming convention (AgoraNet ships `agoranet.z00`, FsxNet `FSXNET.Z00`, Micronet `MICRONET.Z00`, etc.). Additionally, the day-number gating (`num > currentNumber`) permanently rejected files using the `.Z00` placeholder suffix (extracted day=0, gate `0 > 0` = false). Rewritten: Pass 1 prefers `NODELIST.*` filenames; Pass 2 falls back to the newest non-junk file in the configured nodelist area. Both passes gate on `upload_date > MAX(last_seen)` from the `ftn_nodelist` table, handling year wraparound and placeholder extensions. Junk filter (FILE_ID.DIZ, readmes, .nfo, .txt, etc.) prevents misc files from being fed to the nodelist parser. `extractNodelistFromZip` applies the same junk filter when selecting the fallback file inside an infopack ZIP.
- Fix: Echolist/filebone auto-scan reported "0 list(s) updated" and silently re-parsed unchanged archives on every scheduled run because `_importFile` returned `{unchanged: true}` before calling `executeImport`, leaving `last_imported_at` untouched. Added `touchLastImported()` helper on `networkEcholist` and `fileEcholist` models that bumps the timestamp on no-change scans so the next run correctly skips the file via `_isNewer`. Scanner summary now reports "X updated, Y verified (no changes)" so sysops see that work happened even when nothing changed.
- Fix: Echolist scanner second-pass (unzip archive + match configured names) had silent fallthroughs for several failure modes. Added L2 diagnostic logging when: an archive is in `file_entries` but missing on disk (with resolved path), no archive is found at all, and most importantly when the unzip succeeds but no extracted file matches any configured echolist/filebone name (logs extracted contents and configured names side by side so the sysop can see exactly what's inside vs. what's expected).
- Feat: MSGID counter now lives in a dedicated `msgid_day_watermark` Postgres table, one row per day-bucket, replacing the earlier Redis-backed counter. Every serial allocation is a single atomic `INSERT ... ON CONFLICT ... DO UPDATE SET max_counter = max_counter + 1 RETURNING` upsert, with Postgres row-level locking handling cross-process coordination natively. No more Redis TTL management, no more startup re-scan via outbound table enumeration, no more dual source of truth. On first deployment the table is auto-backfilled from existing current-format msg_ids (grouped by day prefix, max counter per day) so the watermark reflects real history immediately. Legacy 11+ char serials from pre-fix installs are ignored during backfill. New `allocateHistoricalSerial(date, sourceTag)` helper lets import tools allocate MSGIDs at the correct chronological day for historical message bases without conflicting with live generation. `getWatermarkForDay(day)` returns the current max counter, message count, and source tag for diagnostics. `source` column distinguishes `'live'` / `'backfill'` / `'import_<label>'` provenance. The watermark table appears in `dbmigrations.js` as an auto-created table via `tablenames.conf`.
- Feat: FTN MSGID system rebuilt around a Canectic epoch (December 8, 1980 UTC, deliberately pre-FidoNet for historical import support) and a tuple storage model. The 32-bit FTS-0009 serial now encodes `days_since_epoch` in the high 16 bits and a shared Redis-backed per-day counter in the low 16 bits, giving a 179-year horizon (wraps in 2160) and 65,536 MSGIDs per day aggregated across all four Canectic processes. On process startup, `initializeMsgidCounter()` seeds the Redis counter from a DB scan of today's highest serial (+100 safety margin) so cold starts, Redis flushes, and fresh installs can't regenerate into used values. `msg_id` storage is split into `(msg_id, msg_orig_addr)` tuple columns so cross-network dupe detection, import-vs-generated collision safety, and cross-post discovery can all be reasoned about via the separate fields. `reply_to` gets the same split for threading consistency. `threadid` stays as a full-string opaque key. The tosser/compose/import paths all update their dupe checks and reply_to lookups to compare tuples. Legacy `"address serial"` rows are backfilled via an idempotent migration in `dbmigrations.js`. ### Upgrade Notes

- **Node 22 or later is now required, and Node 26 is the tested target.** `better-sqlite3` moved to v13, the first release built on N-API, so its native binary is stable across Node major versions instead of being tied to each version's V8 internals. Its `engines` range is what sets the floor. nvm is the recommended way to manage this; `INSTALL.md` leads with it and keeps a native Node install documented as the supported alternative.
- **npm 12, which ships with Node 26, will not run dependency install scripts unless the package is allowlisted.** A plain `npm install` on a new box blocks six packages, three of them the native modules whose install script is the thing that resolves the binary. `package.json` now approves `bcrypt`, `node-pty`, `@serialport/bindings-cpp` and `better-sqlite3`, pinned to version, and denies `msgpackr-extract`, `cpu-features` and `ssh2` deliberately (all three have working pure-JS paths). Pinning means upgrading one of the four approved packages needs a deliberate re-approval, which is exactly when a native module's install script deserves another look. Without the allowlist, password hashing, door games and DOS doors over socat fail at runtime rather than at install time.
- **`allow_netmail_relay` is deprecated and ignored.** It is replaced by `netmail_relay_mode`, taking `off`, `nodelist` or `on`, defaulting to `nodelist`. Every upgrade lands on `nodelist` regardless of what the old boolean said, because it cannot be honoured: `configStore` seeds every default into the `settings` table, so a sysop who deliberately set it false is indistinguishable from one who never touched it. Since relay never worked correctly before this release anyway (the message and packet headers were swapped on every transit message) there is no working configuration to preserve. A system that wants full transit relay sets the mode deliberately on `/admin/config`. Read `docs/sysop/NETMAIL_RELAY.md` before choosing `on`, which is considerably broader than it reads.
- **The one-time MSGID tuple split no longer runs during migrations.** Its predicate is `msg_id LIKE '% %'`, which no index helps, so it full-scanned every per-area message table on every update to establish there was nothing to do. On a hub with hundreds of areas that is minutes per pull. `dbmigrations.js` now checks a marker in `settings` (a single lookup) and prints instructions instead. If your message base predates the `msg_id` / `msg_orig_addr` split, run this once with the worker running:
- **Run `node src/tools/dbmigrations.js` after updating.** New columns this release: `imported` on every per-area messages table (this is what stops imported history being tossed back out to peers), `max_age_days` and `max_messages` on `message_areas` and `message_groups`, `destination_address` on `echomail_bad`, and the `sort_order` / `post_as` columns that were previously created by runtime `ALTER TABLE` statements at gateway startup and are now declared in `db/schema`. New tables: `mailer_sessions`, `outbound_file_log`, `netmail_relay_log`, `update_checks`.
- **Changing the pm2 child interpreter needs a full re-register, not a restart.** The four apps now pin their interpreter at config-eval time instead of resolving a bare `node` from whatever environment the daemon inherited. `pm2 resurrect` replays the old `dump.pm2` and will not pick it up:
- **If you boot via systemd, route the unit through the wrapper.** The unit `pm2 startup` generates bakes an absolute Node path into both `PATH` and every `Exec*` line, which pins the service to whichever Node was current the day it was generated. After `nvm alias default 27` the BBS still boots on the old version, and once that version is uninstalled it stops booting at all. Install the new wrapper outside the repo, because `update.sh` treats `setup/` as a code directory and wipes it:
- **A database created before this release may be SQL_ASCII.** `create_pg_db_user.sh` issued a bare `CREATE DATABASE` with no `ENCODING`, so it inherited `template1`, which on a cluster whose initdb ran under a C or POSIX locale is SQL_ASCII. That encoding performs no validation at all: invalid byte sequences are stored silently and handed back unchanged, so any component writing non-UTF-8 corrupts data without raising an error. Message bodies carry CP437 art and accented names, so this matters in practice. New installs now create with `TEMPLATE template0 ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C'`. Existing installs convert with `setup/convert_db_encoding.sh`, which scans every text column for invalid bytes and refuses up front rather than failing halfway through a restore, verifies row counts table by table, and then swaps the database names so `.env` needs no edit. `--preflight-only` answers whether you need it at all.
- **Upgrading the host OS: read `docs/sysop/OS_UPGRADE.md` first.** An Ubuntu release upgrade installs a new PostgreSQL major but does not migrate the data. The new cluster comes up healthy and empty, nothing errors, and every message base, user record and per-area table stays in the old cluster until someone drops it. The runbook covers the `pg_dropcluster` / `pg_upgradecluster` sequence with port continuity and row-count verification, Redis 7 to 8 (RDB is forward-only, so the dataset does not survive a rollback), native addons, third-party PPAs, and rollback. One thing it records that is easy to miss: a release upgrade can silently remove `build-essential`, which only surfaces on the next clean `npm install`.

- The installer's constraint that it must work with no `node_modules` is checked by walking its import graph rather than by remembering it, and the six destructive install rules were pulled the other way to confirm the suite notices: the .env overwritten when one already exists, the .env left world readable, an existing installation clobbered, the runtime directories not created, a dependency added to the install path, and the art tree enumerated on only one axis.
- The phase sequence is tested by injecting the commands, because without a way to make npm fail on demand there is no way to assert that a failure at the dependency install rolls the files back while one at the steps phase does not, and that rule is the whole reason the sequence has a middle. Nine more reversals checked: the rollback window extended past the migration, no rollback at all, the dump taken before the files rather than before the migration, manual steps run automatically, the board left down after a failure, a cached base trusted without verifying, the protected base evicted, unmeasurable free space treated as none, and connected callers blocking rather than warning.
- The update tool now has tests at the command line, not only under it. Two of the fixes above had no coverage because they lived in a CLI `main()`: the version it reports and whether a named version is checked are both only observable by running the thing. Those tests publish miniature releases into a temp directory and spawn the tool against a temp installation, and they declare whatever migrations the local ledger happens to hold so that a developer's own database cannot decide whether they pass.
- Two real bugs came out of writing these rather than out of review. `NaN || 0` in the Node version comparison turned an unreadable version into zero, so a system whose Node version could not be parsed would have been told every release needed a newer one. And the update check imported `appConfig` as a namespace when it is a default-export singleton, which no unit test would have caught and which failed on the first end-to-end run.
- `npm test` now skips cleanly when PostgreSQL or Redis is unavailable rather than failing 22 tests, so a clean checkout on a machine lacking either can still tell a real regression from a missing service. Both probes race against a bound and swallow the hang as well as the rejection, because each client retries internally and awaiting one in a `before` hook turns a missing service into a hook timeout, which mocha reports as a failure rather than a skip.
